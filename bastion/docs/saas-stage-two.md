# SaaS, этап 2: подключение сервера и адреса

Текущая реализация Bastion рассчитана на изолированную установку Delivest Node. Это описание относится к локальной ветке `codex/saas-stage-two`; на действующие серверы она не отправлена. Контракт установщика согласован с локальным коммитом Node `4eceece` и версией архива `0.2.0`.

## Конфигурация Bastion

- `DELIVEST_NODE_INSTALLER_URL` и `DELIVEST_NODE_INSTALLER_SHA256` закрепляют отдельный HTTPS-скрипт установщика. Архив Node задают `DELIVEST_NODE_ARCHIVE_URL`, `DELIVEST_NODE_ARCHIVE_SHA256`, `DELIVEST_NODE_VERSION`. Установщик исполняется только после проверки SHA256. `DELIVEST_BASTION_URL` — публичный HTTPS-адрес панели, `DELIVEST_CERT_EMAIL` — адрес для Let's Encrypt.
- `DELIVEST_DNS_ENCRYPTION_KEY` — постоянный Base64-ключ из 32 случайных байт для шифрования REG.RU API-пароля в PostgreSQL. Ключ хранится отдельно от БД и должен сохраняться при восстановлении Bastion. Без него запись или чтение учётных данных недоступны.
- Финальный образ Bastion включает `openssh-client`, `sshpass`, `curl`, `ca-certificates` и `sha256sum` для SSH-установки. Установка принимает Ubuntu 24.04 amd64 согласно контракту Delivest Node. Для SSH требуется root либо непрерывный доступ к `sudo -n` без запроса дополнительного пароля.

## Порядок подключения

1. В «Серверах» укажите имя, IP/имя сервера, SSH-порт, логин, пароль или ключ и заранее проверенный отпечаток Ed25519 `SHA256:...`. Bastion сравнивает отпечаток с `ssh-keyscan`, затем подключается только с закреплённым ключом хоста. Старые ssh config/known_hosts не подмешиваются.
2. Задание `provision_node` остаётся локальным в Bastion и не передаётся по каналу Node. SSH-секреты живут только в процессе задания и файлах `0600` во временном каталоге `0700`; каталог очищается по завершении или при гибели задания отдельным наблюдателем. При аварийном завершении всего Bastion оставшиеся приватные каталоги удаляются при следующем запуске. Одноразовый токен передаётся установщику через stdin, не через argv, БД или журнал. На перезапуске Bastion прежнее незавершённое задание отмечается как неизвестное; повтор требует снова ввести SSH-доступ и использует ту же запись ноды.
3. После подключения Node отправляет heartbeat с `infrastructure.ready=true`. Только свежий heartbeat с этой проверкой и действующими учётными данными показывает «Готова». Старый heartbeat без проверки не подтверждает готовность.
4. В «Доменах» добавьте полный адрес, отдельно укажите владельца, родительскую зону и режим DNS. Для внешней зоны при резервировании показывается уникальная TXT-запись `_delivest-verification.<адрес>`. После её публикации и точного совпадения публичных A/AAAA с IP ноды Bastion отправляет `domain_prepare` для конкретной франшизы и ревизии размещения. При освобождении новое резервирование требует новую TXT-запись.
5. Для зоны REG.RU сохраните логин и пароль API, затем нажмите «Проверить подключение». Проверка читает записи, создаёт случайную тестовую TXT-запись, проверяет чтением, удаляет по точному типу/имени/значению и проверяет сохранность соседних записей. Подготовка управляемого адреса добавляет A/AAAA; Bastion учитывает созданные им записи и удаляет только их. Операции используют REG.API 2 `zone/get_resource_records`, `zone/add_alias`, `zone/add_aaaa`, `zone/add_cname`, `zone/add_txt`, `zone/remove_record`; `zone/clear` и `zone/update_records` не применяются. Выходящий IP Bastion должен иметь право API-доступа, а аккаунт — право управления конкретной зоной. При неясном результате записи Bastion требует сверки, не считает её своей автоматически.
6. Node выпускает сертификат и атомарно активирует маршрут. Результат подтверждается Bastion отдельно через публичный HTTPS с проверкой сертификата, ответа и заголовка `X-Delivest-Binding-Id`. Ошибка оставляет адрес в состоянии ошибки, а журнал фиксирует итог внешней проверки. Рабочий адрес нельзя освободить только записью в БД: сначала Node удаляет маршрут командой `domain_release`.

Ожидание DNS опрашивается автоматически раз в минуту. Для витрины Bastion проверяет `/`, для API/админки `/ready`, для медиа TLS и маршрут с допустимым `403` корня S3. Заголовок привязки должен совпасть во всех случаях. Ошибки продления сертификатов Node передаёт через heartbeat и показывает карточка сервера.

## Локальная проверка этой ветки

- На отдельной PostgreSQL 17 в контейнере `bastion-stage2-test-db` с портом `15435` выполнены `TEST_DB_PORT=15435 MIX_ENV=test mix ecto.create` и `TEST_DB_PORT=15435 MIX_ENV=test mix ecto.migrate`; последняя миграция `20261128105056_add_domain_onboarding` прошла.
- `mix compile --warnings-as-errors` прошёл.
- `TEST_DB_PORT=15435 mix test test/bastion/domains_test.exs test/bastion/reg_ru_test.exs test/bastion/node_install_test.exs test/bastion/nodes_test.exs test/bastion_web/live/domain_live_test.exs test/bastion_web/live/node_live_test.exs test/bastion_web/channels/node_channel_test.exs test/bastion_web/channels/instance_channel_test.exs test/bastion_web/live/instance_live_test.exs test/bastion/metrics_test.exs`: 63 теста, 0 ошибок.

Для локальных тестов REG.RU, DNS, HTTPS и SSH использованы фальшивый HTTP-ответ, подставной DNS-резолвер, fake SSH runner и проверка фактического shell bootstrap с локальным файлом. Реальный REG.RU API не вызывался.

**Приёмка отложена по решению владельца:** изолированного Linux-сервера и тестовой зоны REG.RU сейчас нет. Поэтому чистая установка, искусственный обрыв и повтор на сервере, автозапуск после перезагрузки, права API и сохранность чужих записей в реальной зоне, публичный HTTPS, выпуск и продление сертификата, а также доступность соседней франшизы при сбое **не проверялись**. Версии Bastion/Node/Delivest и реальные ID операций стенда фиксируются в будущем протоколе демонстрации; здесь они не подставлены.
