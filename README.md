# Delivest Platform

Общий репозиторий публичного сайта Delivest и панели управления Бастион. История обоих проектов сохранена: исходный лендинг `c4a11a0` и Бастион `10cadd7` входят в историю ветки объединения. Основное приложение ресторанов остаётся в отдельном репозитории.

- `landing/` — статический сайт на Astro. Форма и собственный счётчик обращаются только к публичному API Бастиона через nginx сайта.
- `bastion/` — Phoenix-приложение: управление инстансами, настройки лендинга, заявки и аналитика.
- `docs/` — взаимодействие приложений и переход со старых установок.
- `docker-compose.yml` — общая сеть и существующие сервисы Бастиона; лендинг включается профилем `landing`.

## Разработка и проверки

Для лендинга нужен Node.js 22.23.4 или новее (версия закреплена в `landing/.node-version`); сборочный Docker-образ использует ту же версию.

```sh
cd bastion
mix deps.get
mix phx.server
# В отдельном терминале из корня репозитория:
cd landing
npm ci
npm run dev
```

Dev-сервер Astro проксирует `/api/landing/` в локальный Бастион (по умолчанию `http://127.0.0.1:4000`). Для другого порта задайте `BASTION_API_URL` при запуске Astro. Запросы браузера остаются на домене лендинга.

```sh
cd landing
npm test
npm run build
# Из корня: адресные серверные тесты (параметры локальной БД по необходимости)
cd bastion
mix test test/bastion_web/landing_test.exs test/bastion/landing_yandex_test.exs
```

CI проверяет приложения отдельными заданиями, собирает отдельные образы и публикует их только для изменённого приложения после попадания в `main` или при выпуске тега `v*`. Автоматического деплоя нет.

## Развёртывание

### Установка выбранного выпуска на ресторан

Сначала выпустите агент с поддержкой `release_manifest_v1`, затем примените миграции Bastion и включите новый экран. Старый агент показывает необходимость обновления: его можно один раз обновить прежней отдельной командой «Обновить агента»; если она недоступна или конфигурация образа не поддерживается, установите новый агент вручную на сервере ресторана. Пока агент не заявил поддержку протокола, Bastion не разрешает обновление сайта.

На вкладке «Обновления» укажите точную версию опубликованного GitHub Release основного `ShafranovKirill/delivest` без `v` (например, `1.2.3`). Bastion загружает `release-manifest.json`, проверяет root SHA, gitlinks и digest трёх ожидаемых образов, затем сохраняет комплект по версии. При следующем ресторане та же версия берётся из сохранённого комплекта, даже если вышел новый релиз. Неуспешная загрузка или неполный manifest останавливает подготовку до создания бэкапа и команды агенту.

Экран показывает целевую версию и ID последней команды, подтверждённую версию и digest server/client, версию и digest агента, а также последнюю ошибку. «Обновить агента» остаётся отдельной операцией; агент с новым протоколом требует выбрать версию и для неё. При переподключении Bastion повторно отправляет незавершённую команду с прежним ID и сохранённым комплектом. Агент возвращает ход или сохранённый результат без повторного запуска установки. Если после перезапуска агент не может завершить попытку, ошибка остаётся в истории, а прежняя успешная версия сохраняется в состоянии отката.

Из двух репозиториев обмен можно проверить локально командой `./scripts/test-release-protocol.sh` в корне `delivest`. Нужны локальный тестовый PostgreSQL (`TEST_DB_PORT`, по умолчанию `55442`) и версии Erlang/Elixir из `delivest/agent/.tool-versions`; тест использует временную сборку Bastion на OTP 28 и не подключается к реальным ресторанам.

Для новой установки скопируйте `.env.example` в `.env` **в корне**, задайте реквизиты Бастиона и оба домена. Не переносите production автоматически на новую структуру: сначала прочитайте [инструкцию перехода](docs/platform-migration.md).

```sh
# Сначала серверная часть; миграции выполняются при старте контейнера.
docker compose up -d --build bastion postgres s3
# Затем публичный сайт; не перезапускает Бастион.
docker compose --profile landing up -d --build --no-deps landing
```

Оба приложения используют одну сеть Compose. Не меняйте Compose project name при переходе: от него зависят имена томов. База и хранилище Бастиона остаются прежними. TLS настраивается отдельно для каждого домена: `bastion/deploy/host-nginx.sh` и `landing/deploy.sh` читают корневой `.env`. Эти команды меняют сервер и запускаются только при согласованном деплое.

Контракт API и устройство аналитики: [docs/landing-analytics.md](docs/landing-analytics.md).
